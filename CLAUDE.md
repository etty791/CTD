# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A real-time "Kung Fu Chess" game in Python: there are no turns — any piece may be ordered to move at any time, moves take real time to travel (1000 ms per square, `DEFAULT_MOVE_DELAY_MS`), and pieces collide mid-flight. The game ends when a king is captured.

It runs two ways: **local** (one process, `main.py`, GUI drives the engine directly) and **networked** (FastAPI WebSocket server owns the authoritative engine and ticks it; a client REPL + the same OpenCV GUI play over the wire, with accounts, Elo, rooms, matchmaking, and observers).

## Commands

The venv is at `.venv` (Windows). Dependencies: pytest, opencv-python (cv2), numpy, fastapi, uvicorn, pydantic, websockets — there is no requirements.txt.

```powershell
.venv\Scripts\python.exe -m pytest                          # all tests (pytest.ini sets testpaths=tests)
.venv\Scripts\python.exe -m pytest tests/test_board.py      # one file
.venv\Scripts\python.exe -m pytest tests/test_collisions.py::TestEnemyPathCollision::test_earlier_starter_wins_head_on   # one test
.venv\Scripts\python.exe main.py                            # local single-process game (OpenCV GUI)
.venv\Scripts\python.exe -m uvicorn server.main:app         # the game server (ws://127.0.0.1:8000/ws)
.venv\Scripts\python.exe -m client                          # networked client: REPL, then the GUI once a game starts
```

Env overrides: `CTD_DB_PATH` (SQLite file, default `server/data/ctd.db`), `CTD_SERVER_URL` (client target, default `ws://127.0.0.1:8000/ws`).

The text tester (`textTester/script_runner.py: run_script()`) reads a script from stdin: a `Board:` section of tokens (`.`, `wK`, `bP`, ...) followed by a `Commands:` section (`click x y`, `jump x y`, `wait ms`, `print board`).

## Architecture

Layered, one direction of dependency:

```
view / input / textTester ─┐
                           ├─→ game_engine ─→ rules + real_time ─→ model
server ────────────────────┘        │                  │
   │                                └──────────────────┴─→ events
   └─→ shared ─→ model
client ─→ shared + view + input          (never game_engine / real_time / rules)
```

Each layer has exactly one job — don't let responsibilities leak across these boundaries:

- **`model/`** — dumb domain state and simple transitions; no rule validation. `Board` wraps an 8x8 grid whose cells hold either a `Piece` or the string sentinel `EMPTY_CELL = '.'` (import it from `model.board`; never compare to a literal). `Piece` carries `id`, `Color`, `PieceType`, `position`, and a `State` enum: `idle`/`moving`/`captured`/`airborne` plus two cooldown states, `long_rest`/`short_rest` (`state.is_resting()` is true for either). `Position(x, y)` is **x = row, y = col**. Board mutation goes through `get_piece_at`/`set_piece_at`/`move_piece`/`place_piece`/`is_cell_empty`; both `move_piece` and `place_piece` apply pawn promotion, but neither marks captures — a displaced occupant's `State.captured` transition is the arbiter's job (`RealTimeArbiter._mark_captured`), not `Board`'s, since only the arbiter can also evict that occupant's own pending move (see the vacate-on-move gotcha below). `model/game_snapshot.py` defines the view-facing `PieceDTO` — beyond `id`/`position`/`type`/`color`/`state`, it carries `origin`, `target`, and `progress` (0.0-1.0) so the view can render a piece mid-flight, plus `move_start_ms`/`move_arrival_ms` (the move's absolute clock bounds, `None` when idle) so a consumer that renders faster than it receives snapshots — the networked client — can recompute `progress` for itself instead of trusting a sampled value; all collapse to the piece's own position/0.0/`None` when idle or resting.
- **`rules/`** — pure, timeless move legality. `rules_engine.validate_move(board, src, dst)` returns a frozen `MoveValidation(is_valid, reason)` dataclass. Reasons come from the `MoveReason` StrEnum in `rules/rules_config.py` (`OK`, `EMPTY_SOURCE`, `ILLEGAL_PIECE_MOVE`, `GAME_OVER`, `PIECE_RESTING`, `INVALID_MOVE`, `INVALID_JUMP`) — never a bare string literal; StrEnum members compare equal to their value, so `reason == "ok"` still works. It dispatches to per-piece strategy classes in `piece_rules.py` (`_SlidingRules` shared by Rook/Bishop/Queen). No time, no collisions, no mutation here.
- **`events/`** — `EventBus`: a minimal **synchronous** pub/sub keyed on event type (`subscribe`/`unsubscribe`/`publish`); a handler that raises is logged and skipped so it can't block the remaining handlers. `events/game_events.py` holds the frozen event dataclasses: `GameStarted`, `GameEnded(winner)`, `MoveStarted`, `MoveCompleted`, `MoveTruncated` (a move shortened mid-flight by a same-color blocker, carrying its new `target`/`arrival_time_ms`), `MoveAborted` (a move that ended without its piece ever reaching a new cell — blocked at origin, or invalidated on arrival), `PieceCaptured`, `RestEnded` (a cooldown elapsed; the piece is back to `State.idle`), `ScoreChanged`. The arbiter is the only publisher of move/capture/end events; everything reactive (scores, move log, scene overlays, sounds, server-side finalization, network broadcasting) subscribes rather than being called directly.
- **`real_time/real_time_arbiter.py`** — the heart of the game: timing, pending moves, path-collision resolution, and post-move cooldowns. Owns a millisecond `clock` and a `pending_moves` list. `add_move`/`add_jump` enqueue a `Move` with an arrival time (`distance * DEFAULT_MOVE_DELAY_MS`) and a unique `move_id`; a jump is a `Move` whose origin == target. **`piece.state` is the single source of truth for the in-flight lock**: `add_move`/`add_jump` reject any piece that is not `State.idle` (this includes resting pieces, via `is_resting()`), and flip it to `moving`/`airborne` on acceptance. Time only advances via `advance_time(ms)`, which (1) resolves path collisions — same color: the later-arriving piece is truncated one square before the shared cell (publishing `MoveTruncated`, or `MoveAborted` if it's blocked before its first step); opposite colors: the **earlier** arriver at the shared cell is captured mid-flight (the later piece "sweeps" it); airborne pieces capture enemy movers that enter their square during the jump window — then (2) applies arrived moves, re-validating each against the current board (`_is_still_valid`; a move that fails is aborted via the shared `_abort_move` helper, publishing `MoveAborted`), then (3) calls `_release_expired_rests()` (publishing `RestEnded` per piece released). A piece never returns straight to `idle` when a move concludes: `_begin_rest` puts it into `long_rest` or `short_rest` (durations `LONG_REST_DURATION_MS`/`SHORT_REST_DURATION_MS` in `real_time_config.py`) anchored to the move's `arrival_time` (not the current clock, so rests behave identically regardless of how coarsely `advance_time` is called); `_release_expired_rests` flips it back to `idle` once the rest has elapsed. A piece captured while resting is dropped, never revived. Returns True when a king is captured. It publishes through the optional `event_bus` (`_publish` is a no-op when none was passed, so tests can construct an arbiter bare); each `PieceCaptured` carries the `capturing_move_id` that caused it, which is how `MoveLog` correlates a capture with its move.
- **`game_engine/game.py`** — `KungFuChessGame`, the facade the UIs talk to: `move_request`, `jump_request` (both return `MoveValidation(False, MoveReason.PIECE_RESTING)` if the piece is on cooldown), `wait(ms)` (the only thing that drives the arbiter clock), `finish_game`, `game_active`, `get_snapshot()`. It owns the `EventBus` (`game.events`) and wires the subscribers that live in `game_engine`: `ScoreTracker` (`score_config.PIECE_VALUES`, tallies `PieceCaptured` and re-publishes `ScoreChanged`; KING is deliberately unscored — a king capture ends the game instead) and `MoveLog` (ordered `MoveLogEntry` list, `was_capture` correlated by `move_id`). `game_engine/snapshot.py`'s `GameSnapshot` exposes `get_all_pieces()` (the `PieceDTO` list, cross-referencing the arbiter's `pending_moves` for `origin`/`target`/`progress`) and `get_scores()`; it lives in `game_engine` rather than `model` because it needs `real_time` knowledge that `model` must not depend on.
- **`input/` & `textTester/`** — UI, input handling, and script parsing only; no game rules or state mutation here. `Controller` turns pixel clicks into select-then-move requests (left click = move, right click = jump) and only ever reads `game.board` through `is_within_boundaries`/`is_cell_empty`/`get_piece_at`; `BoardMapper` converts pixels ↔ grid coordinates.
- **`view/`** — OpenCV GUI: `GUI_runner.run_GUI(game)` wires `AssetManager` (loads `board.png` and per-piece/per-state sprite folders under `view/assets/`), `GameRenderer` (draws a frame from a snapshot of `PieceDTO`s plus the side score panels), `PieceAnimator` (per-piece-id, picks the sprite frame for a `PieceDTO`'s state — `STATE_ASSET_FOLDER` in `view_config.py` maps every `State` to its asset folder, including `long_rest`/`short_rest` — advancing frames by elapsed wall-clock time since the piece entered that state, looping or clamping per the asset's `graphics` config; `prune()` drops tracked pieces no longer in the snapshot), `SceneAnimator` (board-level intro/victory overlays driven by `GameStarted`/`GameEnded`, keyed by scene name via `SCENE_ASSET_FOLDER`; a non-looping scene dismisses itself when its frames run out), `SoundPlayer` (one `winsound` fire-and-forget clip per event type via `SOUND_ASSET_MAP`; missing files just log a warning), and `GameLoop` (cv2 window, mouse callback, drives `wait` on a wall-clock cadence). `GameRenderer._pixel_position` lerps a piece's pixel position between `origin`/`target` by `progress`, so in-flight pieces animate smoothly across frames even though each `render_frame` call only sees a stateless snapshot.
- **`shared/`** — the wire contract, imported by **both** sides. `protocol.py`: the `Envelope(type, payload, game_id)` every WebSocket frame is wrapped in, plus the `MessageType` enum (`register`/`login`/`create_room`/`join_room`/`play`/`move`/`jump`/`state`/`game_start`/`game_over`/`resign`/`error`/...). `messages.py`: the pydantic payload model per message type (`CredentialsPayload`, `AuthAckPayload`, `MovePayload`, `JumpPayload`, `GameStartPayload`, `GameOverPayload`, `StatePayload`, ...) — these depend on `model/` **only**, so encoding a `GameSnapshot` into a `StatePayload` lives in `server/encoding.py` instead. `PiecePayload` carries `move_start_ms`/`move_arrival_ms` instead of a sampled `progress` — since `STATE` is sent on change rather than on a timer, a fraction frozen at encode time would never animate between frames — and `StatePayload.server_time_ms` is the clock those times are measured against. `protocol_config.py`: only values both sides must interpret identically (`Status`, `Role`, `ROOM_STATUS_WAITING`, `MATCH_TIMEOUT_MS`); server-only knobs stay in `server/server_config.py`.
- **`server/`** — FastAPI + WebSockets; the authoritative engine per game. `main.py` accepts sockets on `WS_PATH`, validates each frame into an `Envelope`, and hands it to `dispatch`; its `lifespan` starts/stops the `PersistenceWorker`; on `WebSocketDisconnect` it forfeits the player's live game (or detaches an observer / leaves a room). `dispatcher.py` is a `MessageType → coroutine` table filled by the `@register(...)` decorator — `main.py` imports `server.handlers` purely for that side effect. `handlers.py` holds the module-level singletons (`registry`, `room_manager`, `clock`, `persistence`, `logged_in_usernames`) and one handler per message. `connection.py` wraps a socket with an `asyncio.Lock` so a broadcast task and a handler reply can't interleave frames. `session.py`'s `PlayerSession` binds a username to a `Connection`.
  - `game_session.py` — `GameSession`: two players (+ observers), a `KungFuChessGame`, server-side ticking (`AsyncClock.every` → `engine.wait(elapsed_ms)` every `TICK_MS`), and the end-of-game → Elo → `GAME_OVER` pipeline behind two idempotent gates (`_ended` for the Elo submission, `_finalized` for the broadcast+cleanup). Broadcasting is **event-driven, not tick-driven**: the engine still advances real time every tick, but `_on_tick` only calls `broadcast_state()` when the engine's bus published one of `STATE_CHANGING_EVENTS` during that tick (subscribed via `_mark_dirty`, which just raises a flag so several events in one tick still cost a single frame) or when `MAX_STATE_INTERVAL_MS` has passed without one (a resync heartbeat). `broadcast_state()` itself resets that flag/timer, so an out-of-band send (a move handler's immediate echo, the initial frame at game start) counts as the heartbeat instead of leaving a duplicate queued for the next tick. It must **not** know about `GameRegistry` or `RoomManager` — registry/room cleanup is injected as the async `on_finalize` callback.
  - `rooms.py` — `RoomManager`, pure and synchronous, no I/O: explicit rooms (`create_room` mints a short Crockford-base32 id, creator = White, second joiner = Black, later joiners = observers) and the ELO seek pool (`seek` pairs within `MATCH_ELO_RANGE`). It returns result objects (`RoomJoinResult`, `SeekResult`, `LeaveResult`) that the async handler layer acts on; timeouts and notifications are the handlers' job. `Role` (player/observer) and `Color` stay separate concepts.
  - `async_clock.py` — the one timing source for everything server-side (`every` for game ticks, measuring real elapsed ms off the loop clock rather than assuming `tick_ms`; `after` for the matchmaking timeout), so timing can be faked wholesale in tests.
  - `elo.py` — pure Elo math (`K_FACTOR = 32`, `DEFAULT_RATING = 1200`), no I/O.
  - `persistence/` — `PersistenceWorker` owns the `Database` + `UserRepository` on **one** dedicated thread (`ThreadPoolExecutor(max_workers=1)`): sqlite connections are thread-affine and scrypt hashing is CPU-heavy, so neither may touch the event loop. Jobs are submitted as `Future`s (`future.result()` from sync code, `await asyncio.wrap_future(...)` from async). `user_repository.py` returns result objects (`CreateUserResult`, `AuthResult`, `GameResultRatings`); `password_hashing.py` is stdlib scrypt with a per-user salt and a constant-time compare; every SQL string, scrypt parameter, and the `AuthReason` vocabulary live in `persistence_config.py`.
- **`client/`** — `python -m client`: `Shell` is a dispatch-dict REPL (`register`/`login`/`play`/`room [id]`/`help`/`quit`) that hands off to the same OpenCV GUI once a game starts. `ServerConnection` owns a background daemon thread running its own asyncio loop and the `websockets` client; sends are marshalled onto it with `run_coroutine_threadsafe`, while inbound frames either go straight to the active `RemoteGame` (`STATE`/`GAME_OVER`) or onto a queue the main thread blocks on (`wait_for`, which polls in bounded slices so Ctrl+C stays responsive). A `STATE` that arrives before `set_active_game` has run is held (`_pending_state`) and replayed the moment a game attaches, rather than dropped — frames are no longer guaranteed within `TICK_MS`, so losing one could leave the board looking empty until the next real change. `RemoteGame` implements exactly the surface `view/` and `input/` expect from a local `KungFuChessGame` (`move_request`/`jump_request`/`wait`/`get_snapshot`/`game_active`/`events`/`board`), so the GUI and `Controller` run unchanged over the network for players and observers alike; `RemoteGameState` is one decoded frozen frame doubling as the snapshot and the piece index, and `RemoteBoardView` is the read-only slice of `Board` the controller needs. Since a frame's `progress` is not on the wire (see `shared/`), `RemoteGameState.get_all_pieces()` recomputes it every call from each piece's `move_start_ms`/`move_arrival_ms` against `server_time_ms` plus wall-clock time elapsed since the frame was received, clamped to 1.0 past arrival — this is what keeps motion smooth at render rate even though frames themselves arrive sparsely. The client never imports `game_engine`/`real_time`/`rules` state — the server is authoritative.

## Coding rules

- **Encapsulation**: touch board state only via `Board`'s public API (`get_piece_at`, `set_piece_at`, `is_cell_empty`, ...) — never `board._grid[...]` from outside `Board`. Prefix class-internal state and private helpers with a leading underscore.
- **No magic values**: business logic contains zero raw numbers or literal strings — board dimensions, timing delays, asset properties, error messages, SQL, and protocol literals live in module-level constants or config modules (e.g. `DEFAULT_MOVE_DELAY_MS`, not `1000`; `MoveReason.PIECE_RESTING`, not `"piece_resting"`; `ERROR_NOT_IN_GAME`, not the sentence).
- **Result objects over exceptions**: high-level checks and actions return domain result objects like `MoveValidation`, `AuthResult`, `LeaveResult` instead of raising. When a truly exceptional error occurs, raise a domain-specific exception (e.g. `InvalidMoveError`, `UnknownRoomError`, `PersistenceNotStartedError`) — never a raw `Exception`, and never signal errors by returning `False`/`None` silently. Preserve existing public interfaces.
- **SRP & DRY**: each function does one thing (`validate_move` / `execute_move`, not one `process_move` that validates + mutates + times); each piece of logic lives in exactly one place.
- **Naming**: `snake_case` `verb_noun` functions (`validate_move`, `advance_time`), `PascalCase` classes/enums.
- Use type hints and `dataclasses` for all new code; pydantic `BaseModel` for anything that crosses the wire.
- **Sync core, async edge**: the engine, arbiter, rules, and `RoomManager` stay synchronous and I/O-free. Only `server/` (handlers, `GameSession`, `AsyncClock`, `Connection`) and `client/network.py` are async; blocking work (sqlite, scrypt) goes through `PersistenceWorker`, never the event loop.

## Testing

- Tests live in `tests/` and mirror the source structure. Test public behaviors, not private helpers; use pytest fixtures and parameterized helpers to set up boards and game states. The suite is currently green (496 passed, 1 xfailed).
- Cover: move validation and rejection reasons (assert on `MoveValidation.reason`), arbiter timing/path/collision resolution, published events, game lifecycle (`game_active`, `finish_game`, `wait`), and the server (protocol payloads, rooms/matchmaking, handlers, `GameSession`, Elo, persistence).
- Tests are deterministic: they never sleep — they construct boards directly (`Board([[EMPTY_CELL]*8 ...])`), enqueue moves, and call `advance_time(ms)` explicitly. Server tests fake the clock (recording `.every`/`.after` callbacks and firing them by hand) and the persistence worker, and drive scheduled `create_task` work to completion with a `flush_tasks()` helper rather than waiting on it.
- `async def` tests work **without pytest-asyncio**: `tests/conftest.py` installs a `pytest_pyfunc_call` hook that runs each coroutine test via `asyncio.run`. (Its docstring's claim that `EventBus` is asyncio.Queue-backed is stale — the bus is synchronous.)
- `tests/ultra_tests.py` is not picked up by the default run (it doesn't match `test_*.py`); it's a standalone scenario script.

## Gotchas (current state, 2026-07)
- `piece.position` duplicates the grid location; `set_piece_at` and `move_piece` keep it in sync — never set one without the other.
- **A mid-flight piece vacates its origin square** the instant its first step completes (`RealTimeArbiter._vacate_departed_origins`, at `move.start_time + DEFAULT_MOVE_DELAY_MS`) — other pieces then pass through or land on that cell as if the mover weren't there. `piece.position` is *not* updated by this (it still reads the origin until the piece actually lands), so anything reasoning about "where is this piece" for rules purposes must go through `rules_engine.validate_piece_move(board, piece, destination)` (keyed off the piece, not a board cell) rather than `validate_move(board, source, destination)`, which requires a non-empty source. Airborne (jumping) pieces never vacate — they stay on their square for the whole jump window so they can keep intercepting. A move that can no longer complete does **not** return to its vacated origin: `_abort_move`/`_retreat_vacated_move` walks backward along the move's own path to the nearest free square (publishing `MoveTruncated`) or, if none is free, the piece is captured outright. Because a vacated piece is absent from the board, `GameSnapshot.get_all_pieces()` must also union in any of `arbiter.pending_moves` not already found by the board scan, reporting them at `move.origin`, or they'd flicker out of existence mid-move.
- **Capture is single-sourced in the arbiter.** `RealTimeArbiter._mark_captured(piece, capturing_move_id)` is the only place a piece becomes `State.captured` — it's idempotent and evicts the piece's own pending `Move` (`_drop_moves_for`) so a corpse can never again truncate, capture, or be re-captured (the "ghost move" bug this guards against: a piece killed at its (still-occupied, pre-vacate-fix) origin used to leave its old move in `pending_moves` forever). `Board.move_piece`/`place_piece` never set `State.captured` themselves — callers that care about a displaced occupant must call `_mark_captured` before mutating the board.
- A piece never goes `moving`/`airborne` → `idle` directly: every completed move or jump routes through `long_rest`/`short_rest` first (see `RealTimeArbiter._begin_rest`). Code that checks "is this piece free to command" must use `state.is_resting()` / `state == State.idle`, not just check for `moving`/`airborne`, or it'll let you re-issue a move during cooldown.
- `GameSnapshot`/`PieceDTO` and `GameRenderer` assume `origin`/`target`/`progress` are always populated (defaulting to the piece's own position and `0.0` when idle) — new `State` values need an entry in `STATE_ASSET_FOLDER` (`view/view_config.py`) or `PieceAnimator.frame_for` will `KeyError`.
- The arbiter can publish `GameEnded` **twice** for one game (once from path-collision resolution, once from arrival). Every subscriber must be idempotent — that's what `GameSession._ended` guards, so only one Elo job is ever submitted.
- `server/handlers.py`'s `registry` / `room_manager` / `clock` / `persistence` / `logged_in_usernames` are module-level singletons resolved at call time. Tests must reassign them (`handlers.registry = GameRegistry()`, see the autouse `reset_handler_state` fixture) rather than importing the names directly.
- `shared/` must never import `game_engine`, `real_time`, or `server` — the client depends on it. Anything needing a live engine (snapshot → `StatePayload`) belongs in `server/encoding.py`.
- Observers are tracked in two places: `GameSession.observers` (for broadcasts) and `GameRegistry._player_to_game` (so `get_game_for_player` resolves them). `GameSession` can't reach the registry, so callers of `game.add_observer` must call `registry.add_observer` alongside it.
- `handle_move`/`handle_jump` in `server/handlers.py` reach into `game.engine.board` for the "is this your piece" check — a known layering violation, flagged with a `TODO` in the file. Ownership belongs behind the engine facade.
- `STATE` broadcasts are event-driven (see `server/game_session.py`'s `STATE_CHANGING_EVENTS`/`_mark_dirty`), so a state-mutating code path that forgets to publish an event is invisible to clients until the next `MAX_STATE_INTERVAL_MS` heartbeat. Anything the arbiter does to a piece outside of `MoveStarted`/`MoveCompleted`/`PieceCaptured`/`GameEnded` needs its own event (`MoveTruncated`, `MoveAborted`, `RestEnded` exist for exactly this reason) or it'll appear to lag by up to a second on the wire.
